# YooPost 중단 원인과 복구 검증 — 2026-10-06

## 확인된 원인

Slack 접수, Claude 세션 생성, 실제 작성 시작, GitHub 발행 요청, 실제 게시 완료를 구분해 추적하는 장치가 부족했다.
HTTP 요청에 성공해도 뒤 단계가 시작·완료됐다는 뜻은 아니었다.

| 경로 | 중단·중복 가능 조건 | 적용한 복구 |
|---|---|---|
| Slack → GitHub | Slack 재전송 헤더가 있으면 무조건 무시; KV 조회와 저장 사이에 중복 요청 가능 | 전달 ID별 Durable Object 직렬 저장; 저장 실패는 503으로 재전송 요청 |
| GitHub 전달 | dispatch 성공 뒤 실행이 취소되거나 요청 기록 전에 종료 | 원고 브랜치 저장 후 Python 확인 응답까지 기다림; 같은 ID 재전송 |
| Claude 시작 | 세션 생성 응답은 성공했지만 `started` 기록이 없음 | 요청 기록 직후 PC와 무관한 15분 타이머 등록; 실제 작성 시작 여부 확인 |
| Claude 연결 | 인증·설정 오류가 Codex 인계에서 제외됨 | 독립 인증을 사용하는 Codex 인계 허용; 응답 유실·서버 오류는 15분 확인 후 인계 |
| 원고 작성·검증 | 검증 보고서 집계·대표 원문 URL 형식 불일치; 한 카테고리 실패가 연속 작성을 막음 | 공유 검증 규칙, 한 번 보정, 다른 실행 가능한 카테고리 계속 작성; 기존 품질 검사 유지 |
| 승인 → 발행 | dispatch 접수 후 runner 중단; `approved` 상태에 남음 | 발행 완료까지 15분 타이머; 같은 원고 ID로 재확인 |
| Blogger 응답 | 글이 올라갔지만 응답·상태 저장 유실; insert 자동 재전송 | 숨은 원고 ID로 기존 글을 먼저 찾아 상태·결과 알림 복구; insert 자동 반복 제거 |
| 늦은 저장 | 이미 발행·제외·보류된 상태를 대기·실패로 덮음 | 최종 상태 보호; 발행 실행기에서도 미승인·보류 원고 거절 |
| Worker 재시작 | 상태만 저장되고 복구 알람이 저장되지 않는 틈 | SQLite Durable Object 트랜잭션으로 상태와 알람 함께 저장 |
| 장애 알림 | Slack 장애 중 알림 실패를 이미 알림 완료로 취급 | 실제 전달 성공 후 완료 표시; 실패한 알림만 재시도 |

## 운영 동작

- 자동 승인은 원고 메시지 게시 후 60초다. 자동 승인한 원고는 **🤖✅ 자동 승인 (1분 경과)**를 유지한다.
- ✅ 수동 승인은 즉시 처리한다. ❌ 보류된 원고는 자동 승인과 재시도에서도 발행하지 않는다.
- 수동 지시 전달 실패는 1분 뒤, 요청 기록 확인이 없으면 10분 뒤 같은 전달 ID로 재전송한다. 최대 5회 후 실패를 알리고 기록을 보존한다.
- 발행 dispatch 실패는 1·2·4·8·15·30분 간격 최대 7회(약 1시간, 영구 오류는 즉시 중단 — 2026-10-19), 승인 후 발행 완료 미확인은 15분 간격 최대 5회다. 상한 후 실행·인증 확인 알림을 남기며 ✅로 다시 시도할 수 있다.
- Codex 인계 정기 확인은 GitHub에서 30분마다 실행한다. 요청별 미시작 타이머는 별도로 Cloudflare에서 동작한다.
- 본문 원고 ID가 같은 게시글은 새로 만들지 않는다. 게시글 목록을 읽지 못하면 중복 확인 없이 발행하지 않는다.
- 원고 품질·사실 검증 실패, 인증 취소, 외부 서비스 장기 중단을 성공으로 표시하지 않는다. 요청과 원고를 남기고 필요한 조치를 알린다.

## 검증 기록

- 로컬 전체 Python 테스트: **361 통과, 1 건너뜀**, 커버리지 **96.95%**. 이후 Claude 서버 오류·시작 기록 경계 검증을 추가한 관련 테스트 **39개 통과**.
- Node Slack/Worker 테스트: **55개 통과**. 동시 재전송, 프로세스 재시작, 저장 트랜잭션 실패, 승인 경쟁, 상태 저장 실패, 반복 알림을 포함한다.
- [마지막 수정까지 GitHub Linux 전체 테스트](https://github.com/rkdghkclgns-design/YooPost/actions/runs/37418196128): **Python 363개 통과**, 커버리지 **96.97%**, Slack 중계 테스트 job도 성공.
- Cloudflare Worker 버전 **65a0f57a-9051-4a4d-bb75-cfb571f328b1**, 배포 **4f4c0918-b979-442c-b8c4-2f1bb0f4a158**, 운영 트래픽 100%에서 새 전달 큐·발행 확인 기능을 확인했다.
- 실제 전달 확인 검사: Worker 저장 **201** → 영속 알람 → [GitHub 실행](https://github.com/rkdghkclgns-design/YooPost/actions/runs/37418272794) 성공 → Python 확인 응답 → Worker **accepted**, 시도 **1회**. 원고 작성·발행 없이 전달 경로만 검사했다. 같은 전달 ID를 다시 보내도 **accepted**, **1회**를 유지했다.
- 기존 요청 `C0C50SP7VV5-1791259338398959`: 7개 카테고리 모두 `published`, 모두 `approved_by=auto-60s` 확인. [Slack 진행 카드](https://yoopost.slack.com/archives/C0C4ZUG0TC5/p1791259363102139)는 **7/7**이며 7개 행 모두 자동 승인 표시를 확인했다.

PC를 실제 종료하는 테스트는 수행하지 않았다. 작성·승인·발행·복구 타이머는 GitHub-hosted runner와 Cloudflare에 배포돼 있으며,
운영 전달 확인 검사도 해당 클라우드에서 완료됐다. 외부 사업자의 서비스 중단이나 계정 권한 취소를 포함한 무조건적인 성공은 보장할 수 없다.

## 구현 근거

Slack은 실패·시간 초과 이벤트를 다시 전송하므로 재전송을 같은 지시로 처리해야 한다. [Slack Events API](https://docs.slack.dev/apis/events-api/)

Durable Object의 알람은 재전송될 수 있으며, 상태와 알람의 저장은 SQLite 트랜잭션으로 함께 수행할 수 있다.
[Cloudflare 알람](https://developers.cloudflare.com/durable-objects/api/alarms/),
[SQLite 저장 API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)
